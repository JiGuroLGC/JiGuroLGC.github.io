最近在重构一个老项目的时候，我发现代码里充满了各种"聪明的写法"。这些代码出自不同时期、不同的人之手，但都有一个共同特点：**过度设计**。

## 场景一：万能的工厂模式

我们有一个简单的通知模块，功能就是发送站内信、邮件和短信。最初的实现非常简洁——三个函数，每个函数几十行代码。

后来有一天，一位同事说："我们应该用工厂模式，这样以后加新的通知渠道更方便。"

于是代码变成了这样：

```typescript
interface INotificationFactory {
  createSender(): INotificationSender;
}

class EmailNotificationFactory implements INotificationFactory {
  createSender(): INotificationSender {
    return new EmailSender();
  }
}

class SMSNotificationFactory implements INotificationFactory {
  createSender(): INotificationSender {
    return new SMSSender();
  }
}
```

最终结果是：一个本来 100 行的模块，膨胀到了 500 行，增加了 6 个接口和 8 个类。而所谓的"以后加新渠道"——项目运行了三年，从来没有发生过。

> 设计模式是工具，不是信仰。在你确实需要它之前，不要引入它。

## 场景二：过度抽象的 Hook

另一个例子是前端的自定义 Hook。我们有一个表单页面，包含三个输入框。原本直接使用 `useState` 管理状态就足够了。

但有人写了一个"通用的"表单 Hook：

```typescript
function useForm<T extends Record<string, any>>(initialValues: T) {
  const [values, setValues] = useState<T>(initialValues);
  const [errors, setErrors] = useState<Partial<Record<keyof T, string>>>({});
  const [touched, setTouched] = useState<Partial<Record<keyof T, boolean>>>({});

  const handleChange = useCallback((field: keyof T) => (value: any) => {
    setValues(prev => ({ ...prev, [field]: value }));
    if (touched[field]) {
      // 验证逻辑...
    }
  }, [touched]);

  const handleBlur = useCallback((field: keyof T) => () => {
    setTouched(prev => ({ ...prev, [field]: true }));
  }, []);

  // ... 还有 50 行
  return { values, errors, touched, handleChange, handleBlur };
}
```

一个只有三个字段的表单，被这个 Hook 绕得眼花缭乱。新人需要花半天时间才能理解数据是怎么流动的。

## 过度设计的代价

过度设计不是免费的。它带来的问题包括：

1. **理解成本增加**：新人需要先理解你的抽象层，才能开始工作
2. **维护负担加重**：更多的代码意味着更多的 bug 和更多的测试
3. **灵活性降低**：过度抽象的代码往往更难以修改
4. **效率下降**：写代码的时间花在了架构上，而不是功能上

## 何时需要抽象

我不是说不要使用设计模式和抽象。关键是要在合适的时机使用：

- **第三次出现时再抽象**：Rule of Three——同一模式出现三次时，才考虑抽取公共逻辑
- **先写具体实现，再重构**：过早的抽象往往是错误的抽象
- **让需求驱动设计**：不要为了"万一以后需要"而写代码

## 好代码的标准

我越来越觉得，好代码的标准其实很简单：

你的代码应该让下一个读它的人（包括六个月后的你自己）能够轻松理解。如果一段代码看起来很"聪明"，那么它很可能不够"好"。

简单不是简陋，清晰不是肤浅。写出简单清晰的代码，往往比写出复杂的代码更难。

因为简单需要判断力——知道什么该做，什么不该做。而这恰恰是区分优秀开发者和普通开发者的关键。
