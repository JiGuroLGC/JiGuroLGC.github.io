## 二、换思路：网络抓包

首先我们要知道，一个软件的图片加载方式只有两种：

| 方式 | 说明 |
|:---:|---|
| 本地加载 | 图片存储在设备本地 |
| 网络加载 | 图片从服务器按需拉取 |

某对的加载方式显然是第二种。我们完全可以通过  **网络抓包** 的方式，对某对进行抓包，从而获取该图片。

### 抓包原理简要

| 步骤 | 操作 |
|:---:|---|
| ① 设置代理 | 将手机网络流量导向中间节点（本地 VPN 服务） |
| ② 拦截流量 | 抓包软件作为"中间人"，读取所有进出的网络数据包 |
| ③ 解析内容 | 对数据包解码，记录请求地址、头信息、参数、响应内容等 |
| ④ HTTPS 解密 | 通过安装自定义证书解密 HTTPS 流量（需手动信任证书） |
| ⑤ 记录与展示 | 将信息以列表或详情形式呈现，供分析调试 |
| ⑥ 返回软件 | 将原数据包或修改过的数据包封装伪装，返回给软件 |

简而言之：**抓包软件让手机流量"绕道"经过它，从而读取并记录网络通信内容。**

### 实际操作

了解这些后，我们就可以正确使用抓包软件了。  
首先，我们使用 **JustTrustMe++** 模块，对某对的 SSL 证书检查机制进行 hook，使其能够信任我们的证书。

这里使用大家熟知的 **小黄鸟（HttpCanary）** 进行抓包，打开小黄鸟，设置目标软件为某对。

我们点击右下角按钮，使小黄鸟进入小窗模式，并打开某对，回到之前的解析页面。

## 三、深入分析：缓存目录与加密

### 3.1 分析请求规律

我们先分析抓包得来的数据，能够发现：

> - 当我们点击解析的某一张图时，某对会先向 `https://kd-book.cdnjtzy.com/scanimg/scan` GET 这张图片和这张图片前后的两张图，总共是 **三张图** 。
> - 当我们向右滑时，每滑动一下，某对都会 GET 下一张图之后再展示。
> - 已经向数据包请求过的图像，即使返回之前的图像页，某对也 **不会向服务器二次请求** —— 因此滑动时没有加载圆圈，也并无卡顿。

### 3.2 推断缓存位置

那么我们可以合理推想：当我们已经查看过一张图片时，某对一定会将其 **缓存在某目录** ，如果用户返回查看，就可以直接使用缓存图片，而不是重复请求浪费服务器资源。这是很多软件非常正常的做法。

所以现在有了思路，最大的问题是找出缓存文件夹在何处。由于这是软件的基础功能，不可能向用户要文件读写权限来缓存在公用目录。所以只有一种可能：  
某对将图片缓存到了 `/data/user/0/com.kuaiduizuoye.scan/`  或 ` /storage/emulated/0/Android/data/com.kuaiduizuoye.scan/` 两个私有目录下。

| 候选目录 | 权限要求 |
|---|---|
| `/data/user/0/com.kuaiduizuoye.scan/` | root |
| `/storage/emulated/0/Android/data/com.kuaiduizuoye.scan/` | 无需 root |

我们当然可以进入私有目录，直接查找后缀为 `.jpg` 的图片（由抓包数据可知）。我们在 `/storage/emulated/0/Android/data/com.kuaiduizuoye.scan/` 目录中，搜索到了 20 多个结果，可以发现 **几张置灰的图片** ，非常可疑，且数量刚好是 3。

<img src="https://icdn.binmt.cc/2510/68de00febb062.jpg">

我们定位到目录：
`/storage/emulated/0/Android/data/com.kuaiduizuoye.scan/files/image/`

目录里除了刚刚的 3 张图，还存在某对本身的许多图标，这就更能佐证缓存目录的猜想了。

我们打开图片查看，发现管理器提示—— **"图片损坏"** 。

<img src="https://icdn.binmt.cc/2510/68de011d4a4eb.jpg">

> 这又是怎么回事？

### 3.3 验证缓存目录

让我们再次测试，这是否确实是缓存目录？我们回到某对，从刚刚点击的图片开始逐个向左滑。发现，**每向左滑一张图，目录里就多一张灰图** ，且每个灰图文件的大小和抓包得出的真实图片大小相差无几。

那么看来，这确实就是缓存目录了，这些损坏的图片也确实就是解析图片。那为什么他们会损坏呢？

有经验的同学到这里一眼就能看出来：**这些图片肯定经过了什么特殊的处理** ，比如加密或是转译。

<img src="https://icdn.binmt.cc/2510/68de015ea981f.jpg">

### 3.4 初步 16 进制分析

我们可以用 MT 的 **16 进制编辑器** 对损坏图片文件进行查看：

| 检查项 | 结果 |
|:---:|---|
| 文件头 | `FF D8 FF DB` — 常见 JPEG 文件头 |
| 文件尾 | `FF D9` — 正常 JPEG 文件尾 |
| 显示 | 图片损坏 |

文件头尾都没问题，那理论来说这张图片就是可以被解析的。但问题是显示损坏，那么看来 **中间的数据信息被修改了** ，这需要进一步分析。

<img src="https://icdn.binmt.cc/2510/68de01809f8d8.jpg">

我们注意到，这些损坏图片的命名存在规律。图片以 **`xxxxxxxx_TRANSITION2.jpg`** 命名。我们到 dex 中搜索字符串 `TRANSITION2`，尝试找出加密函数。

<img src="https://icdn.binmt.cc/2510/68de019f8a512.jpg">

### 3.5 定位加密相关代码

只有一个结果，我们转成 Java 看看：

```java
// 导入包省略...
public class v {

    public static File b(String str) {
        PatchProxyResult proxy = PatchProxy.proxy(
            new Object[]{str}, (Object) null, changeQuickRedirect,
            true, 15154, new Class[]{String.class}, File.class);
        if (proxy.isSupported) {
            return (File) proxy.result;
        }
        return new File(DirectoryManager.getDirectory(a),
            "" + TextUtil.md5(str) + "_TRANSITION2.jpg");
    }
}
```

代码大致意思是，根据输入的字符串 `str`，生成一个缓存图片文件对象（`.jpg`），命名方式是图像的 **MD5 值** ，再以固定后缀 `_TRANSITION2.jpg` 结尾，用于进行图像过渡或加密。但方法中并没有提到具体的加密算法。

## 五、JPEG 编码协议科普

为了防止看不懂输出信息，这里也有必要普及一下 **JPEG 编码协议** 。

实际上，JPEG 文件就是许多 **"小盒子"摞起来** 的。想象 JPEG 是一摞快递盒，每个盒子上都贴着标签（段标记，**Marker** ），告诉你里面装的是啥：

| 标记 | 含义 |
|:---:|---|
| `FF D8` | **SOI** — 图像开始（永远打头，相当于"身份证照片页"） |
| `FF E0` | **APP0** — JFIF 标准标记 |
| `FF DB` | **DQT** — 量化表 |
| `FF C0` | **SOF0** — 帧开始（里面藏着宽高） |
| `FF C4` | **DHT** — 哈夫曼表 |
| `FF DA` | **SOS** — 扫描开始（紧跟着就是真正的压缩流） |
| `FF D9` | **EOI** — 图像结束（最后两个字节） |

每个标记都是两字节，十六进制表示，固定以 **`FF`** 开头。

假设有一张 JPEG 图片，你能看到这样的文件头：

```text
FF D8 FF E0 00 10 4A 46 49 46 00 01 01 01 00 48 00 48 00 00 ...
 │    │    │  │  └─ "JFIF\0" ASCII
 │    │    │  └── 本段长度 16 字节
 │    │    └───── APP0 段标记
 │    └─────────── E0 表示 JFIF 标准
 └─────────────── SOI（图像开始）
```

## 六、发现真相：重复的 SOI

> 现在你懂了吗？

通过分析图片比对信息，我们可以发现，这张图片存在 **两个 SOI** ：

| 偏移 | 标记 | 说明 |
|:---:|:---:|---|
| `0x0000` | `FF D8` | 第一个 SOI，正常 |
| `0x0090` | `FF D8` | **又一个 SOI** ，绝对不应该出现 |

损坏图片前面（`0x8C-0x8F`）刚好是上一个 SOF0 段（帧内信息）的末尾。也就是说：

> **第一个帧的语法还没结束就被强行截断** ，导致结构错位。

从 `0x0090` 开始，某对把同一张图的 **DQT、SOF0、DHT、SOS** 又原样复制了一份，最后导致图片解析错误。

### 修复方法

所以，`0x0090` 处的第二个 `FF D8` 是 **非法的** ，应把它连同后面那份 **完全重复** 的 DQT/SOF0/DHT/SOS 全部删掉：

| 操作 | 说明 |
|:---:|---|
| 保留 | `0x0000–0x008B` 那一段（合法的第一帧头） |
| 删除 | `0x0090` 开始的重复 SOI + 完整表数据 |
| 接回 | 后面真正的 SOS 数据（`0x02D8` 开始） |

这样文件才能合法。

后续分析其他的损坏图片文件，其实它们都是这样的。  
知道了解决方法，那现在就可以来解决问题了。
